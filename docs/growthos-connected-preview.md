## Credential-handling incident

The connected Supabase configuration and API-key listing responses returned sensitive credential material in connector output. The owner subsequently stated that the keys have been rotated; that assertion, retirement of the exposed credentials, and the updated consumers have not been independently verified here. Values are deliberately not recorded. Creating a new key alone does **not** invalidate a legacy key. Review provider audit logs and access to the connector response history, and follow the organization's incident procedures.

As partial containment, the fifth migration revoked `service_role` privileges on the five GrowthOS tables, all seven GrowthOS functions and the activity sequence. On the connected database, catalog checks found no service-role table privileges (SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER), sequence privileges (USAGE, SELECT, UPDATE) or function EXECUTE; anon EXECUTE was also denied on all seven functions. Authenticated EXECUTE was retained only for the owner predicate and the three intended RPCs; their authorization checks and RLS remain essential. An owner-claim transaction after the migration inserted a prospect and task and verified both audit triggers; it was rolled back. Four enquiries remained, and the named QA prospects were absent. This is not full containment: the exposed key may still have elevated access to other project resources, including enquiries. Do not treat the grant change as a substitute for rotation.

### Coordinated rotation runbook (owner action required)

Do not put secrets in chat, source, connector inputs, logs or this report. Inventory all consumers and environments before retiring anything: live and preview deployments, server jobs, Edge Functions, webhooks, other websites and applications, and any Supabase Auth SMTP configuration. The website's enquiry store currently reads `SUPABASE_SERVICE_ROLE_KEY` and uses raw REST requests with both `apikey` and `Authorization: Bearer` headers; verify compatibility with a new Supabase secret key before switching. Supabase's new keys are not JWTs, and some integrations require changes to how headers are sent. Test with the actual existing deployment's code; do not assume this repository's preview behavior establishes production compatibility.

1. In Supabase **Settings > API Keys**, create a new secret key for each backend consumer and ensure clients use a publishable key instead of legacy anon. Store and enter values directly in provider dashboards or a secret manager. In Vercel, update the relevant server-only variables in each affected environment, including `SUPABASE_SERVICE_ROLE_KEY` where appropriate; update publishable-key variables as needed. Check variable precedence, every consumer, and deployment-specific settings. Supabase documents the [legacy-key migration](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) and [compromised-key procedure](https://supabase.com/docs/guides/security/rotate-leaked-api-keys).
2. Vercel environment changes apply only to **new deployments**. Verify a new preview using the new configuration, then coordinate a production credential-only redeployment and smoke test for every affected deployment before retiring legacy keys. This conflicts with the current prohibition on production redeployments unless the owner expressly approves a security exception; merely changing settings does not update the current deployment. An immediate compromise risk may justify faster revocation with accepted downtime, at the owner's incident-response discretion. Old deployment URLs will keep old environment values. See [Vercel rotation guidance](https://vercel.com/docs/environment-variables/rotating-secrets).
3. After verifying all consumers, deactivate the legacy keys and follow Supabase's instructions to rotate signing keys and revoke trust in the legacy JWT secret. Deactivation affects **both** legacy anon and service-role keys; revoking a JWT signing secret can affect active sessions or integrations, so plan and verify the migration. Re-enabling compromised legacy keys restores exposure. Consult the current [Supabase signing-key guidance](https://supabase.com/docs/guides/auth/signing-keys).
4. For SMTP, use Brevo **Settings > SMTP & API > SMTP** to create a replacement, then enter it directly into Supabase Auth's custom SMTP settings and any other affected SMTP consumers; verify authentication mail before deleting the compromised key. Brevo says deletion is irreversible and can interrupt mail if a consumer still uses it. The website's enquiry notifications use the separate `BREVO_API_KEY` HTTP API credential, not the SMTP password; inventory and rotate that API key separately if exposed or shared, updating the corresponding server-only Vercel environment. See [Brevo SMTP key management](https://help.brevo.com/hc/en-us/articles/7959631848850-Create-and-manage-your-SMTP-keys) and [Supabase custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
5. Confirm completed rotation without sending any values. Then test owner authentication, a real non-owner account, public enquiry persistence and notification delivery, and all preview regressions, using agreed temporary test data and cleanup. A real non-owner test requires an authorized test account; do not share passwords or session tokens in chat.
